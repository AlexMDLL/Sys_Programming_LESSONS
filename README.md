# Пара 13. Архитектура параллельных задач

Стартовый проект: обработка множества текстовых файлов по схеме
Producer–Consumer (производитель → очередь заданий → пул обработчиков → сбор результатов).

## Структура

```
FileProcessingPipeline/
├── FileProcessingPipeline.sln
├── FileProcessingPipeline/
│   ├── Program.cs                  — меню, отчёт, сохранение report.json
│   ├── Models/
│   │   ├── FileTask.cs             — задание: Id + путь
│   │   ├── FileAnalysisResult.cs   — результат с WorkerId
│   │   ├── FileProcessingError.cs  — ошибка обработки
│   │   └── AnalysisReport.cs       — итоговый отчёт
│   ├── Services/
│   │   ├── TextCounter.cs          — строки/слова/символы
│   │   ├── FileAnalyzer.cs         — анализ одного файла
│   │   ├── SequentialProcessor.cs  — последовательная обработка
│   │   ├── PipelineProcessor.cs    — TODO: конвейер с обработчиками
│   │   └── ReportService.cs        — сборка отчёта
│   └── Data/file1..file4.txt       — тестовые файлы
├── FileProcessingPipeline.Tests/
│   └── TextCounterTests.cs
└── t/Пара 13. Архитектура параллельных задач.md
```

Запуск:

```
dotnet run --project FileProcessingPipeline               # интерактивное меню
dotnet run --project FileProcessingPipeline -- --seq      # только последовательно
dotnet run --project FileProcessingPipeline -- --workers 4
dotnet run --project FileProcessingPipeline -- --errors 2  # один файл недоступен
dotnet run --project FileProcessingPipeline -- --compare   # сравнение 1/2/4/8
dotnet test
```

## П1. Разделение обязанностей

1. Модель задания `FileTask` (Id + путь), коллекция из 10 заданий.
2. Анализ одного задания через `FileAnalyzer.AnalyzeAsync`.
3. Независимый обработчик `WorkerAsync(int workerId, FileTask task)`.
4. Запуск нескольких обработчиков через массив `Task` и `Task.WhenAll`.
5. Сбор результатов в `ConcurrentBag<FileAnalysisResult>`.
6. Распределение разных заданий между обработчиками.

В коде это TODO 1–5 в `PipelineProcessor`:

1. Создать канал и передать в него задания, закрыть запись.
2. Запустить `workerCount` обработчиков.
3. Организовать получение заданий из канала.
4. Дождаться завершения всех обработчиков.
5. Измерить общее время выполнения.

## П2. Поведение системы и ошибки

1. Количество обработчиков: проверить 1, 2, 4, 8.
2. Обработать ошибочное задание (несуществующий файл): ошибка попадает в `Errors`,
   остальные задания продолжают обрабатываться, программа не падает.
3. Статистика исполнителей: сколько заданий выполнил каждый Worker.
4. Сравнить последовательную и параллельную обработку, ответить на вопросы:
   почему один обработчик медленнее последовательного, почему больше обработчиков
   не всегда быстрее, как влияет объём данных, зачем контролировать нагрузку.
5. Анализ архитектуры: как изменится система для 10 000 изображений.

Запрещено: пустой `catch {}`, обычный `List<T>` для конкурентной записи,
запуск задач без ожидания.

## Анализ архитектуры: 10 000 изображений

Если вместо текстовых файлов обрабатывать 10 000 изображений, схема остаётся той же,
меняются только содержимое задания и работа обработчика:

| Компонент | Ответственность |
| --- | --- |
| Producer | обходит каталог, формирует задания `FileTask` и пишет их в канал |
| Задание | id, путь к изображению, требуемая операция (например, эскиз 256×256), параметры сжатия |
| Канал | `Channel<FileTask>` с ограниченной ёмкостью: producer не убежит вперёд обработчиков |
| Worker | читает файл, декодирует изображение, выполняет ресайз, сохраняет результат |
| Результат | id задания, имя файла, размеры, время обработки, `WorkerId`, путь к результату |
| Ошибки | `IOException`/`UnauthorizedAccessException` ловятся на уровне задания и попадают в `Errors` |
| Отчёт | общее время, число успешных и неуспешных, статистика по обработчикам |

Что придётся изменить по сравнению с текстовым вариантом:

1. **Задание** должно знать, что делать с файлом: операция и её параметры, иначе один
   пул не сможет обрабатывать разные варианты (эскиз, поворот, сжатие).
2. **Обработчик** становится дороже: декодирование изображения нагружает процессор и
   память, поэтому число обработчиков ограничивают не только ядрами, но и объёмом RAM.
3. **Нагрузка** контролируется строже: ограниченный канал и `FullMode = Wait` не дают
   производителю загрузить в память всё сразу; при 10 000 файлов это критично.
4. **Ошибки** обрабатываются на уровне задания: одно битое изображение не должно
   останавливать конвейер, а должно попасть в отчёт с типом и текстом ошибки.
5. **Результаты** пишутся на диск самими обработчиками, а в отчёт идёт только метаданные,
   иначе `ConcurrentBag` накопит мегабайты данных.
6. **Диск и CPU** — два узких места: при большом числе обработчиков упор идёт в диск,
   поэтому конфигурацию подбирают экспериментально (как в `--compare`).

Схема:

```
Producer (обход каталога)
        │  FileTask
        ▼
Channel<FileTask> (ограниченная ёмкость)
        │
   ┌────┴────┬─────────┐
   ▼         ▼         ▼
Worker 1  Worker 2  Worker N   (декодирование → ресайз → сохранение)
   │         │         │
   └────┬────┴─────────┘
        ▼
ConcurrentBag<результат> + ConcurrentBag<ошибка>
        │
        ▼
ReportService → отчёт + report.json
```
