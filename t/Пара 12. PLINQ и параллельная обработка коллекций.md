
в этом уроке мы не управляем отдельными итерациями цикла, а описываем последовательность операций над данными — фильтрацию, преобразование и агрегацию. PLINQ распределяет эту работу между несколькими потоками.


### Что такое PLINQ

PLINQ (Parallel LINQ) - технология .NET для параллельной обработки последовательностей с использованием LINQ.

```cs
//Подключается через пространство имён:
using System.Linq;

// Обычный LINQ:
var result1 = numbers
    .Where(x => x > 10)
    .Select(x => x * 2)
    .ToList();

// PLINQ:
// AsParallel() переводит последовательность в параллельный запрос ParallelQuery<T>
var result2 = numbers
    .AsParallel()
    .Where(x => x > 10)
    .Select(x => x * 2)
    .ToList();
```

#### Что произойдёт, если добавить `AsParallel()` к коллекции из пяти элементов?
```spoiler
PLINQ попробует организовать параллельную обработку, но накладные расходы могут оказаться выше выигрыша. Само наличие `AsParallel()` не гарантирует ускорения.
```
### `Where` и `Select`

Операции знакомы по обычному LINQ, но теперь их обработка может выполняться параллельно.
```cs
// фильтрует элементы по условию.
var kills = events
    .AsParallel()
    .Where(e => e.Type == "Kill");

// преобразует каждый элемент.
var scores = events
    .AsParallel()
    .Select(e => e.Points);

// Операции можно объединять:
var result = events
    .AsParallel()
    .Where(e => e.Type == "Kill")
    .Select(e => e.Points)
    .ToList();
```

#### Если в `Where` используется тяжёлое вычисление, поможет ли PLINQ?
```spoiler
да, если обработка элементов независима и расходы на распараллеливание окупаются.
```
### `Aggregate`
```cs
int[] numbers = { 1, 2, 3, 4 };

// операция свёртки последовательности в одно итоговое значение.
int sum = numbers.Aggregate(
    0,
    (current, number) => current + number);
```

```cs
// Для PLINQ есть перегрузка `Aggregate`, позволяющая использовать локальные аккумуляторы и объединять их результаты.
int sum = numbers
    .AsParallel()
    .Aggregate(
        0, // начальное значение аккумулятора.
        (localSum, number) => localSum + number, // лямюда-функция добавляет элемент к локальному результату.
        (first, second) => first + second, // объединяет частичные результаты.
        result => result); // преобразует итоговый аккумулятор в конечный результат.
```

#### Почему нельзя использовать одну общую переменную `sum` внутри параллельного `Select` или `Where`?
```spoiler
При несколько потоков могут одновременно изменять одну переменную. Это побочный эффект и потенциальная ошибка синхронизации.
```
### `AsOrdered`
```cs
// По умолчанию PLINQ не гарантирует сохранение порядка исходной последовательности.
// Порядок элементов в `result` может отличаться от исходного.
var result = events
    .AsParallel()
    .Where(e => e.Type == "Kill")
    .ToList();
```

```cs
// Если порядок важен:
// `AsOrdered()` просит PLINQ сохранить исходный порядок элементов в результате упорядоченного запроса.
// За это могут возникнуть дополнительные расходы.
var result = events
    .AsParallel()
    .AsOrdered()
    .Where(e => e.Type == "Kill")
    .ToList();
```
#### Если после `AsParallel()` вызвать `OrderBy`, нужен ли `AsOrdered()`?
```spoiler
обычно нет, если задача состоит именно в сортировке по ключу: `OrderBy` задаёт нужный порядок результата самостоятельно.
```
### Побочные эффекты и стоимость параллелизма

Побочный эффект - изменение состояния за пределами локального результата вычисления: общей переменной, коллекции, файла, консольного вывода и т. п.

Плохой пример:

```cs
var results = new List<int>();

numbers
    .AsParallel()
    .ForAll(number =>
    {
        // Ошибка: List<T> не предназначен
        // для одновременного изменения потоками.
        results.Add(number * 2);
    });
```

```cs
// Безопаснее использовать результат самого запроса:
// Также не стоит считать, что PLINQ всегда быстрее LINQ.
var results = numbers
    .AsParallel()
    .Select(number => number * 2)
    .ToList();
```

Для маленьких коллекций, простых преобразований и запросов с большим количеством зависимостей обычный LINQ часто оказывается предпочтительнее.

PLINQ особенно полезен, когда:
- данных достаточно много;
- обработка одного элемента требует заметных вычислений;
- обработка элементов независима;
- результат можно объединить без сложной синхронизации.

#### Что произойдёт, если распараллелить фильтрацию десяти элементов по простому условию?
```spoiler
скорее всего, накладные расходы не окупятся.
```

```cs
namespace GameEventsAnalyzer;

public static class GameEventGenerator
{
    private static readonly string[] EventTypes =
    {
        "Kill",
        "Death",
        "Loot",
        "LevelComplete"
    };

    public static List<GameEvent> Generate(
        int count,
        int seed = 12345)
    {
        if (count < 0)
        {
            throw new ArgumentOutOfRangeException(nameof(count));
        }
		// Генератор тестовых данных с фиксированным seed.
        var random = new Random(seed);
        var events = new List<GameEvent>(count);
        DateTime start = new(2026, 1, 1, 12, 0, 0);
        for (int i = 0; i < count; i++)
        {
            string type = EventTypes[random.Next(EventTypes.Length)];

            int points = type switch
            {
                "Kill" => random.Next(50, 201),
                "Death" => 0,
                "Loot" => random.Next(5, 51),
                "LevelComplete" => random.Next(100, 501),
                _ => 0
            };

            events.Add(new GameEvent(
                Id: i + 1,
                PlayerId: random.Next(1, 101),
                Type: type,
                Points: points,
                Timestamp: start.AddSeconds(i)));
        }

        return events;
    }
}
```

```cs
namespace GameEventsAnalyzer;
// LINQ.
public static partial class GameEventAnalyzer
{
    public static List<PlayerStatistics> AnalyzeWithLinq(
        IEnumerable<GameEvent> events)
    {
        ArgumentNullException.ThrowIfNull(events);

        return events
            .Where(e => e.Type == "Kill")
            .GroupBy(e => e.PlayerId)
            .Select(group => new PlayerStatistics(
                PlayerId: group.Key,
                KillCount: group.Count(),
                TotalPoints: group.Sum(e => (long)e.Points)))
            .OrderByDescending(x => x.TotalPoints)
            .ToList();
    }
}
// PLINQ.
// Для учебного проекта это удобный пример, 
// но при очень больших объёмах данных 
// группировка и сортировка могут потребовать значительной памяти и времени.
public static partial class GameEventAnalyzer
{
    public static List<PlayerStatistics> AnalyzeWithPlinq(
        IEnumerable<GameEvent> events)
    {
        ArgumentNullException.ThrowIfNull(events);
		// GroupBy, Select и OrderByDescending здесь выполняются в рамках PLINQ-запроса.
		// Итоговый список уже отсортирован по сумме очков, поэтому `AsOrdered()` 
		// для сохранения исходного порядка событий нам не требуется.
        return events
            .AsParallel()
            .Where(e => e.Type == "Kill")
            .GroupBy(e => e.PlayerId)
            .Select(group => new PlayerStatistics(
                PlayerId: group.Key,
                KillCount: group.Count(),
                TotalPoints: group.Sum(e => (long)e.Points)))
            .OrderByDescending(x => x.TotalPoints)
            .ToList();
    }
}
```

### `Program.cs`

```cs
namespace GameEventsAnalyzer;

internal class Program
{
    static void Main()
    {
        Console.WriteLine("=== Game Events Analyzer ===");

        List<GameEvent> events =
            GameEventGenerator.Generate(
                count: 1_000_000,
                seed: 12345);

        Console.WriteLine($"Всего событий: {events.Count:N0}");

        var linqResult =
            GameEventAnalyzer.AnalyzeWithLinq(events);

        var plinqResult =
            GameEventAnalyzer.AnalyzeWithPlinq(events);

        Console.WriteLine();
        Console.WriteLine("Топ игроков:");

        foreach (var player in plinqResult.Take(10))
        {
            Console.WriteLine(
                $"Игрок {player.PlayerId}: " +
                $"убийств {player.KillCount}, " +
                $"очков {player.TotalPoints}");
        }

        Console.WriteLine();

        bool same = linqResult
            .SequenceEqual(plinqResult);

        Console.WriteLine(
            $"Результаты LINQ и PLINQ совпадают: {same}");
    }
}
```

Примечание: `SequenceEqual` здесь корректен, потому что оба запроса заканчиваются одинаковой сортировкой по очкам. При равных очках порядок игроков не определён одинаково, поэтому для строгого сравнения нужно добавить вторичный ключ сортировки:

```
.OrderByDescending(x => x.TotalPoints)
.ThenBy(x => x.PlayerId)
```

Добавьте его в оба метода. Тогда одинаковые результаты будут иметь одинаковый порядок и тест сравнения станет надёжнее.

### Типичная ошибка: побочные эффекты

Покажите студентам неправильный вариант:

```cs
public static List<int> GetPlayerIdsWrong(
    IEnumerable<GameEvent> events)
{
    var result = new List<int>();

    events
        .AsParallel()
        .ForAll(e =>
        {
            // ОШИБКА: несколько потоков
            // одновременно изменяют List<int>.
            result.Add(e.PlayerId);
        });

    return result;
}
```

`List<T>` не гарантирует безопасность одновременной записи из нескольких потоков. Возможны потерянные данные, некорректное состояние коллекции и исключения.

Правильнее использовать сам результат PLINQ-запроса:

```cs
public static List<int> GetPlayerIds(
    IEnumerable<GameEvent> events)
{
    ArgumentNullException.ThrowIfNull(events);

    return events
        .AsParallel()
        .Select(e => e.PlayerId)
        .ToList();
}
```

Задание: исправить неправильную реализацию и объяснить, почему `ToList()` в конце запроса безопаснее, чем ручное добавление элементов в общий список из `ForAll`.

Уточнение преподавателю: `ToList()` материализует результат запроса и собирает элементы в результирующую коллекцию. Не следует переносить внутрь `Select` или `ForAll` произвольные изменения общих объектов — это не делает их потокобезопасными.

## П2

Цель: разобраться с порядком обработки и AsOrdered

В первой практике мы анализировали статистику. Теперь представим, что нужно сформировать игровую ленту событий для просмотра игроком.

Здесь порядок уже важен: события должны отображаться в той последовательности, в которой они находились в исходном журнале.

### Добавляем метод в `GameEventAnalyzer.cs`
Сначала обычный PLINQ без сохранения порядка:
```cs
public static List<GameEvent> GetKillsUnordered(
    IEnumerable<GameEvent> events)
{
    ArgumentNullException.ThrowIfNull(events);

    return events
        .AsParallel()
        .Where(e => e.Type == "Kill")
        .ToList();
}
```

```cs
public static List<GameEvent> GetKillsOrdered(
    IEnumerable<GameEvent> events)
{
    ArgumentNullException.ThrowIfNull(events);
	// PLINQ с сохранением порядка:
    return events
        .AsParallel()
        .AsOrdered()
        .Where(e => e.Type == "Kill")
        .ToList();
}
```

Важное различие:
- `AsParallel()` разрешает параллельную обработку без гарантии сохранения исходного порядка.
- `AsOrdered()` требует сохранять исходный порядок элементов в результате.
- `OrderBy()` сортирует элементы по указанному ключу, а не просто восстанавливает исходный порядок.

### Добавляем сортировку по времени

```cs
// формирует ленту событий по времени
public static List<GameEvent> GetKillsSortedByTime(
    IEnumerable<GameEvent> events)
{
    ArgumentNullException.ThrowIfNull(events);
	// Здесь `AsOrdered()` не нужен: порядок задаётся явно сортировкой.
    return events
        .AsParallel()
        .Where(e => e.Type == "Kill")
        .OrderBy(e => e.Timestamp)
        .ThenBy(e => e.Id)
        .ToList();
}
```

## `BenchmarkRunner.cs`:
```cs
using System.Diagnostics;

namespace GameEventsAnalyzer;
// Чтобы не ограничиваться визуальным сравнением, добавим измеритель времени.
public static class BenchmarkRunner
{
    public static void Compare(
        List<GameEvent> events,
        int repetitions = 5)
    {
        ArgumentNullException.ThrowIfNull(events);

        if (repetitions < 1)
        {
            throw new ArgumentOutOfRangeException(
                nameof(repetitions));
        }

        // Прогрев.
        GameEventAnalyzer.AnalyzeWithLinq(events);
        GameEventAnalyzer.AnalyzeWithPlinq(events);

        var linqTimes = new List<double>();
        var plinqTimes = new List<double>();

        for (int i = 0; i < repetitions; i++)
        {
            var linqTime = Measure(
                () => GameEventAnalyzer.AnalyzeWithLinq(events));

            var plinqTime = Measure(
                () => GameEventAnalyzer.AnalyzeWithPlinq(events));

            if (!linqTime.Result.SequenceEqual(plinqTime.Result))
            {
                throw new InvalidOperationException(
                    "Результаты LINQ и PLINQ не совпадают.");
            }

            linqTimes.Add(linqTime.ElapsedMilliseconds);
            plinqTimes.Add(plinqTime.ElapsedMilliseconds);
        }

        Console.WriteLine();
        Console.WriteLine($"LINQ:  {Median(linqTimes):F3} мс");
        Console.WriteLine($"PLINQ: {Median(plinqTimes):F3} мс");
    }

    private static (List<PlayerStatistics> Result,
        double ElapsedMilliseconds) Measure(
            Func<List<PlayerStatistics>> action)
    {
        var stopwatch = Stopwatch.StartNew();
        var result = action();
        stopwatch.Stop();
        return (result, stopwatch.Elapsed.TotalMilliseconds);
    }

    private static double Median(List<double> values)
    {
        double[] sorted = values.OrderBy(x => x).ToArray();

        int middle = sorted.Length / 2;

        if (sorted.Length % 2 == 1)
        {
            return sorted[middle];
        }

        return (sorted[middle - 1] + sorted[middle]) / 2;
    }
}
```

Вызовите измеритель в `Program.cs`:


Почему PLINQ может проиграть обычному LINQ даже на массиве из миллиона элементов?

Потому что количество элементов само по себе не определяет стоимость работы. Здесь фильтрация и группировка относительно простые, а распределение работы, объединение результатов и сортировка тоже требуют ресурсов. Для более тяжёлых вычислений PLINQ может показать преимущество.

## Дополнительная работа с Aggregate

Чтобы  не ограничиваться только `Where`, `Select` и `GroupBy`, можно выполнить небольшое задание на `Aggregate`.
Создадим общую статистику событий.

Добавьте в `GameEventAnalyzer.cs`:
```cs
public sealed record EventSummary(
    int TotalEvents,
    long TotalPoints,
    int KillCount,
    int DeathCount);
```

Внутри `GameEventAnalyzer` добавьте метод:
```cs
public static EventSummary AnalyzeWithAggregate(
    IEnumerable<GameEvent> events)
{
    ArgumentNullException.ThrowIfNull(events);

    return events
        .AsParallel()
        .Aggregate(
	        // Создание локального аккумулятора
            () => new EventSummaryAccumulator(),
			// Обработка одного элемента
            (local, gameEvent) =>
            {
                local.TotalEvents++;
                local.TotalPoints += gameEvent.Points;
                if (gameEvent.Type == "Kill")
                {
                    local.KillCount++;
                }
                if (gameEvent.Type == "Death")
                {
                    local.DeathCount++;
                }

                return local;
            },
			// Объединение двух аккумуляторов
            (first, second) =>
            {
                first.TotalEvents += second.TotalEvents;
                first.TotalPoints += second.TotalPoints;
                first.KillCount += second.KillCount;
                first.DeathCount += second.DeathCount;

                return first;
            },
			// Получение конечного результата
            result => new EventSummary(
                result.TotalEvents,
                result.TotalPoints,
                result.KillCount,
                result.DeathCount));
}

private sealed class EventSummaryAccumulator
{
    public int TotalEvents { get; set; }
    public long TotalPoints { get; set; }
    public int KillCount { get; set; }
    public int DeathCount { get; set; }
}
```
