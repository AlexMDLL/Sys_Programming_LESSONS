# Введение

Представьте, что наше приложение должно выполнять операции, которые уже реализованы в других программах:

- запускать архиватор для упаковки файлов;
- вызывать системную утилиту для диагностики;
- запускать отдельный инструмент обработки данных;
- получать результат внешней программы и показывать его пользователю.

Вместо того чтобы реализовывать всё самостоятельно, приложение может запустить отдельный процесс операционной системы.

Например, наше приложение запускает `dotnet --info`, получает идентификатор процесса, измеряет время работы и выводит результат.

Чем запуск внешнего приложения отличается от вызова обычного метода C#?
```spoiler
метод выполняется внутри текущего процесса, а внешняя программа запускается операционной системой как отдельный процесс. У неё собственные ресурсы, состояние и жизненный цикл.
```


# Теория

## Процесс и поток

Процесс — выполняющийся экземпляр программы, которому операционная система предоставляет ресурсы и изолированное адресное пространство.

Поток — последовательность выполнения инструкций внутри процесса. Один процесс может иметь несколько потоков.

Пример:

- `MyApp.exe` — процесс;
- главный поток этого приложения — поток;
- `dotnet.exe`, запущенный из `MyApp.exe`, — другой процесс.

При этом асинхронное ожидание через `await` само по себе не означает создание нового потока или процесса.

В C# внешний процесс запускается через `Process`:

```
using System.Diagnostics;

using Process process = new();

process.StartInfo.FileName = "dotnet";
process.StartInfo.ArgumentList.Add("--info");

process.Start();
```

Здесь `Process` — объект .NET, представляющий взаимодействие с процессом ОС. Сам процесс запускается при вызове `Start()`.

Что произойдёт, если вызвать `Start()`, но не дождаться завершения?
```spoiler
Внешняя программа продолжит выполняться независимо от того, перешёл ли вызывающий код к следующим инструкциям.
```

## PID и аргументы

PID (Process ID) — идентификатор процесса в операционной системе. Он позволяет различать процессы, работающие одновременно.

```
process.Start();

Console.WriteLine($"PID: {process.Id}");
```

PID не является постоянным идентификатором приложения: после завершения процесса ОС может повторно использовать его номер.

Аргументы — данные, передаваемые запускаемой программе.

Предпочтительный вариант для построения аргументов в современном .NET — `ArgumentList`:

```
process.StartInfo.FileName = "dotnet";
process.StartInfo.ArgumentList.Add("--info");
```

Каждый элемент добавляется отдельно. Это уменьшает риск ошибок при формировании командной строки с пробелами и специальными символами.

Не следует без необходимости склеивать пользовательские данные в одну командную строку и передавать их внешнему интерпретатору команд.

Что произойдёт, если указать неверные аргументы?
```spoiler
Процесс может успешно запуститься, но завершиться с ненулевым кодом возврата.
```

## Рабочая директория и код возврата

Рабочая директория — каталог, относительно которого внешняя программа может разрешать относительные пути.

```
process.StartInfo.WorkingDirectory =
    Environment.CurrentDirectory;
```

Рабочая директория не обязательно совпадает с каталогом, где находится исполняемый файл.

Код возврата (`ExitCode`) — числовое значение, которое программа сообщает при завершении.

```
await process.WaitForExitAsync();

Console.WriteLine($"Exit code: {process.ExitCode}");
```

Обычно `0` означает успешное выполнение, а ненулевое значение — ошибку. Однако точное значение и его смысл определяются самой запускаемой программой.

Важно: читать `ExitCode` можно после завершения процесса. Поэтому сначала нужно дождаться его завершения.

Что произойдёт, если прочитать `ExitCode` до завершения?
```spoiler
Для запущенного, но ещё работающего процесса .NET выбросит `InvalidOperationException`.
```
## Перенаправление stdout и stderr

У процесса обычно есть три стандартных потока:

- `stdin` — ввод;
- `stdout` — обычный вывод;
- `stderr` — сообщения об ошибках.

При перенаправлении вывода внешняя программа передаёт текст не в обычную консоль, а в потоки, которые может прочитать наше приложение.

```
process.StartInfo.UseShellExecute = false;
process.StartInfo.RedirectStandardOutput = true;
process.StartInfo.RedirectStandardError = true;
```

Для перенаправления в `Process` требуется `UseShellExecute = false`.

Главная проблема: буферы потоков конечны. Если внешняя программа активно пишет в `stdout`, а наше приложение ждёт только завершения процесса, буфер может заполниться. Аналогичная ситуация возможна с `stderr`.

Надёжный подход — начать чтение обоих потоков до ожидания завершения:

```
Task<string> stdoutTask =
    process.StandardOutput.ReadToEndAsync();

Task<string> stderrTask =
    process.StandardError.ReadToEndAsync();

await process.WaitForExitAsync();

string stdout = await stdoutTask;
string stderr = await stderrTask;
```

В этой схеме чтение двух потоков начинается до ожидания завершения. Для обычных утилит это простой способ избежать взаимной блокировки из-за заполненных буферов.

# Демонстрация преподавателя

Для демонстрации используйте `dotnet --info`. Утилита не требует изменения системных файлов и подходит для проверки наличия установленного .NET SDK.

Создайте консольный проект `ProcessDemo` на .NET 9.

```cs
using System;
using System.Diagnostics;

ProcessStartInfo startInfo = new()
{
    FileName = "dotnet",
    UseShellExecute = false,
    RedirectStandardOutput = true,
    RedirectStandardError = true,
    CreateNoWindow = true
};

startInfo.ArgumentList.Add("--info");

using Process process = new()
{
    StartInfo = startInfo
};

var stopwatch = Stopwatch.StartNew();

try
{
    if (!process.Start())
    {
        Console.WriteLine("Не удалось запустить процесс.");
        return;
    }

    Console.WriteLine($"PID: {process.Id}");

    Task<string> stdoutTask =
        process.StandardOutput.ReadToEndAsync();

    Task<string> stderrTask =
        process.StandardError.ReadToEndAsync();

    await process.WaitForExitAsync();

    string stdout = await stdoutTask;
    string stderr = await stderrTask;

    stopwatch.Stop();

    Console.WriteLine($"Длительность: {stopwatch.Elapsed}");
    Console.WriteLine($"Exit code: {process.ExitCode}");

    Console.WriteLine("=== STDOUT ===");
    Console.WriteLine(stdout);

    Console.WriteLine("=== STDERR ===");
    Console.WriteLine(stderr);
}
catch (System.ComponentModel.Win32Exception ex)
{
    stopwatch.Stop();
    Console.WriteLine($"Ошибка запуска: {ex.Message}");
}
```

Продемонстрируйте три ситуации:

1. `dotnet --info` запускается и выводит информацию.
2. В `FileName` указано несуществующее приложение — возникает ошибка запуска.
3. Аргумент заменён на некорректный для выбранной команды — процесс может запуститься, но завершиться с ошибкой.

Разберите различие между ошибкой запуска и ненулевым кодом завершения: это разные этапы и разные причины ошибки.

### Как проверить stderr

Команда `dotnet --info` обычно пишет информацию в `stdout`, поэтому `stderr` может оказаться пустым. Это нормальное поведение, а не ошибка программы.

Чтобы проверить оба потока, можно временно заменить команду на `cmd.exe` с аргументами:

```
startInfo.FileName = "cmd.exe";
startInfo.ArgumentList.Add("/c");
startInfo.ArgumentList.Add(
    "echo Сообщение в stdout & echo Ошибка в stderr 1>&2"
);
```

Этот вариант предназначен для Windows. Он использует `cmd.exe` только в учебном тесте с фиксированной строкой, без пользовательского ввода.

Ожидаемый вывод:

```
=== STDOUT ===
Сообщение в stdout

=== STDERR ===
Ошибка в stderr
```

Код завершения обычно будет `0`, если команда выполнена успешно.

### Почему чтение нужно начинать заранее?

Неправильный вариант:

```
await process.WaitForExitAsync();

string stdout =
    await process.StandardOutput.ReadToEndAsync();

string stderr =
    await process.StandardError.ReadToEndAsync();
```

Если внешний процесс запишет достаточно много данных в один из перенаправленных потоков, он может остановиться в ожидании освобождения буфера. А родительское приложение будет ждать завершения процесса.

Надёжнее сначала запустить чтение обоих потоков:

```
Task<string> stdoutTask =
    process.StandardOutput.ReadToEndAsync();

Task<string> stderrTask =
    process.StandardError.ReadToEndAsync();

await process.WaitForExitAsync();

string stdout = await stdoutTask;
string stderr = await stderrTask;
```

Критерий готовности: студент получает PID, длительность, код завершения, оба потока и может объяснить, почему их чтение начато до ожидания завершения.

# 7. Эталонные решения

## 7.1. Практика № 1 — полное решение

```
using System;
using System.Diagnostics;
using System.ComponentModel;

public class Program
{
    public static async Task Main()
    {
        ProcessStartInfo startInfo = new()
        {
            FileName = "dotnet",
            UseShellExecute = false,
            CreateNoWindow = true,
            WorkingDirectory = Environment.CurrentDirectory
        };

        startInfo.ArgumentList.Add("--info");

        using Process process = new()
        {
            StartInfo = startInfo
        };

        Stopwatch stopwatch = Stopwatch.StartNew();

        try
        {
            if (!process.Start())
            {
                Console.WriteLine("Процесс не запущен.");
                return;
            }

            Console.WriteLine($"PID: {process.Id}");

            await process.WaitForExitAsync();

            stopwatch.Stop();

            Console.WriteLine(
                $"Длительность: {stopwatch.Elapsed}"
            );

            Console.WriteLine(
                $"Exit code: {process.ExitCode}"
            );
        }
        catch (Win32Exception ex)
        {
            stopwatch.Stop();

            Console.WriteLine(
                $"Ошибка запуска: {ex.Message}"
            );
        }
    }
}
```

`Win32Exception` здесь обрабатывает типичную ошибку запуска, например отсутствие исполняемого файла. Это не универсальный обработчик всех возможных ошибок: другие исключения при необходимости должны обрабатываться отдельно в соответствии с конкретным сценарием.

Расширить диспетчер процессов, чтобы после каждого запуска он сохранял запись в файл `process-log.txt`.

Каждая запись должна содержать:

- дату и время запуска;
- имя запущенной программы;

### Дополнительное задание

Добавить ограничение времени выполнения процесса. Если утилита работает дольше установленного лимита, например 10 секунд, приложение должно сообщить о превышении времени.
